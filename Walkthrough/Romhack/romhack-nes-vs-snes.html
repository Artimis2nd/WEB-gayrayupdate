1. คำตอบสั้น

ถ้าเป้าหมายคือ แปลเกมอังกฤษเป็นไทย และยอมแก้ text engine ได้: SFC/SNES ดีกว่า NES/FC ชัดเจน ทั้งเรื่องพื้นที่, RAM, VRAM, ความสามารถด้านกราฟิก และความยืดหยุ่นในการย้ายข้อมูล
แต่ถ้าเป้าหมายคือ เริ่มฝึก reverse engineering ให้เข้าใจเร็ว: NES/FC เรียนรู้ง่ายกว่า เพราะฮาร์ดแวร์และโค้ดเกมมักเล็กกว่า เพียงแต่ข้อจำกัดจะชนเร็วมากเมื่อทำภาษาไทยจริงจัง

2. เปรียบเทียบในมุม "ทำแพตช์ภาษาไทย"

หัวข้อNES / FCSNES / SFCใครได้เปรียบ
CPU8-bit (ตระกูล 6502)16-bit (65C816)SFC
RAM เครื่อง2 KB ภายในเครื่องเป็นหลัก128 KB WRAMSFC มาก
VRAM2 KB nametable + พื้นที่ tile ที่ PPU มองเห็นพร้อมกัน 8 KBVRAM 64 KBSFC มาก
Tile ตัวอักษรโดยทั่วไป 8×8, 2bpp = 4 สี8×8, ใช้ 2/4/8bpp ได้ตามโหมดSFC
สีฟอนต์จำกัดมาก: tile ใช้สีได้ไม่กี่สีตาม paletteฟอนต์ 4bpp ใช้ได้ถึง 15 สีต่อ paletteSFC

โอกาสได้แพตช์ไทยคุณภาพดีทำได้ แต่ต้องประนีประนอมมากทำได้จริงจังกว่าและรักษา readability ได้มากกว่าSFC

NES มี RAM ภายในเพียง 2 KB และ PPU มองเห็นข้อมูล CHR ได้ครั้งละ 8 KiB เท่านั้น (เท่ากับ 512 tile ขนาด 8×8 แบบ 2bpp) ส่วน SFC มี WRAM 128 KB และ VRAM 64 KB ทำให้เก็บ text buffer, tilemap buffer และฟอนต์ระหว่างทำงานได้สบายกว่ามาก (อ้างอิง: NESdev Wiki)

3. ทำไม SFC เหมาะกับภาษาไทยกว่า

1) มีพื้นที่สำหรับ "engine ภาษาไทย"

ภาษาไทยต้องใช้ state มากกว่าอังกฤษ เช่นต้องรู้ว่าตัวก่อนหน้าเป็นพยัญชนะใด, สระนี้เป็นสระบน/ล่างหรือไม่, มีวรรณยุกต์ซ้อนอยู่แล้วหรือไม่, ต้องเลื่อน x/y เท่าไร, บรรทัดเต็มหรือยัง — บน NES แค่ RAM สำหรับทำ buffer ข้อความและสถานะก็เป็นทรัพยากรมีค่ามาก เพราะทั้งเครื่องมีแค่ 2 KB และส่วนหนึ่งถูกเกมเดิมใช้ไปแล้ว บน SFC ย้าย routine เก่าไปเรียก routine ใหม่ แล้วใช้ WRAM ทำงานเป็นขั้นตอนได้สบายกว่ามาก:

อ่านข้อความไทยจาก ROM
  -> decode/control code
  -> วิเคราะห์ตัวประกอบไทย
  -> วาดลง text tilemap buffer ใน WRAM
  -> DMA tilemap/font ที่เปลี่ยนไป VRAM
  -> แสดงผล

2) VRAM ของ SFC ยืดหยุ่นกว่า

NES ล็อกไว้ค่อนข้างมาก: PPU อ่าน CHR ได้พร้อมกันเพียง 8 KB แม้ cartridge จะมี CHR-ROM มากกว่านั้น — ต้องพึ่ง mapper สลับ bank หรือเขียนระบบ CHR-RAM ส่วน SFC มี VRAM 64 KB จึงกันพื้นที่เป็นสัดส่วนได้ เช่น:

VRAM ตัวอย่าง (ตำแหน่งจริงขึ้นกับแต่ละเกม)
$0000-$1FFF  ฟอนต์ไทยสำหรับ dialogue
$2000-$3FFF  tile ฉาก
$4000-$4FFF  tile UI/หน้าต่าง
$5000-$5FFF  sprite
$6000-$7FFF  tilemap ของฉากและกล่องข้อความ

แนวคิดคือมีพื้นที่ให้แยก "ฟอนต์ไทย" ออกจาก graphics อื่นได้ง่ายกว่า

3) รองรับสีและฟอนต์อ่านง่ายกว่า

NES ใช้ tile 2bpp (4 ระดับสี, palette จำกัดมาก) จึงมักทำฟอนต์ไทยที่มีรายละเอียดสูงยาก โดยเฉพาะตัวเล็กและวรรณยุกต์ · SFC ใช้ tile 4bpp ได้ทั่วไป (16 ค่า palette ต่อ tile — ปกติ 15 สี + transparent) ฟอนต์ไทยจึงทำขอบ เงา หรือแยกสีตัวอักษรกับพื้นหลังได้ดีกว่า

4) เพิ่มพื้นที่ ROM ตรงไปตรงมากว่า

SFC ส่วนใหญ่ใช้ LoROM (แบ่ง bank ละ 32 KB) หรือ HiROM (เข้าถึงแบบ linear ได้มากกว่าในบางช่วง address) จึงมักขยาย ROM, วางพื้นที่ script ใหม่ แล้วแก้ pointer 24-bit หรือทำ trampoline/hook ได้เป็นระบบกว่า (แม้ยังต้องเข้าใจ bank/mapping ให้ถูกต้อง)

บน NES การขยาย PRG/CHR มักติดที่: mapper เดิมรองรับขนาดได้แค่ระดับหนึ่ง, bank-switch register เลือกไม่ถึง bank ใหม่, emulator/flashcart อาจไม่รองรับ header ที่ดัดแปลง, pointer 16-bit ข้าม bank ไม่ได้, และฟอนต์มักอยู่ CHR ร่วมกับฉากและ sprite

4. แต่ SFC ก็ไม่ได้ "เพิ่มพื้นที่แล้วจบ"

ข้อจำกัดที่ยังเจอบน SFC:

  • VRAM ไม่ได้มีพื้นที่ว่างเสมอไป — เกมอาจใช้เต็มแล้ว
  • ต้อง upload VRAM ในช่วง VBlank หรือใช้ DMA อย่างระวัง
  • ฟอนต์อาจอยู่ร่วมกับ sprite/UI/ฉาก
  • เกมอาจบีบอัด graphics หรือ script
  • pointer อาจเป็น 16-bit bank-relative ไม่ใช่ 24-bit
  • routine บางเกมสมมติว่าตัวอักษร 1 ตัว = 1 tile เสมอ
  • ถ้าเกมใช้ VWF อยู่แล้ว การเพิ่มอักษรไทยอาจง่ายเรื่องความกว้าง แต่ยากเรื่อง combining marks

ต่างกันตรงที่บน SFC มี "พื้นที่ให้แก้ปัญหา" มากกว่า ส่วน NES มักต้องลดปัญหาให้เล็กลงก่อนจึงจะอยู่รอด

5. แนวทางภาษาไทยที่เหมาะในแต่ละเครื่อง

NES/FC: เป้าหมายควรเป็น "ภาษาไทยแบบประหยัด"

เหมาะกับ: แปลเมนู, แปลชื่อไอเทม, แปลข้อความสั้น, เกมที่มี CHR bank switch ดีอยู่แล้ว (ตระกูล MMC1/MMC3), เกมที่ยอมแทน tile อังกฤษเดิมจำนวนมากได้

แนวทาง: ใช้ตัวอักษรไทย subset เท่าที่จำเป็น · ฟอนต์ 8×8/8×16 ที่กระชับ · แทนที่ glyph อังกฤษ/สัญลักษณ์ที่ไม่ใช้ · ตัดคำแปลให้สั้น · ให้สระ/วรรณยุกต์เป็น tile ประกอบ · ใช้ CHR bank ฟอนต์เฉพาะหน้า dialogue ถ้า mapper ทำได้ · หลีกเลี่ยงการสร้าง glyph ผสมทุกชุด เพราะ CHR จะหมดเร็ว

ตั้งความหวังให้ตรง: ทำได้ แต่อาจต้องยอมให้ตัวอักษรไทยเล็ก, วางวรรณยุกต์ไม่สมบูรณ์ทุกคำ หรือมีเฉพาะชุดอักขระที่พบในบทแปล

SNES/SFC: เป้าหมายควรเป็น "Thai renderer จริง"

เหมาะกับ: แปลเนื้อเรื่องเต็มเกม, RPG ที่มี dialogue ยาว, เกมที่ต้องการฟอนต์อ่านง่าย, งานที่ต้องรองรับสระ/วรรณยุกต์ถูกต้อง, เกมที่มีพื้นที่ ROM และจุด hook engine ได้

แนวทาง: ย้าย script ทั้งหมดไป ROM ส่วนขยาย · ทำ encoding ไทยเฉพาะโครงการ · เขียน parser สำหรับ control code เดิม · เก็บตัวไทยเป็น glyph หลัก + glyph ประกอบ · ทำ routine วางสระบน/สระล่าง/วรรณยุกต์ด้วย offset · ทำ text buffer ใน WRAM ก่อนค่อย DMA เข้า VRAM · ทำ line wrap ตาม pixel/tile width · แยก font dialogue ออกจาก UI หากทำได้

6. เลือกเครื่องตามเป้าหมาย

สถานการณ์คำแนะนำ
อยากฝึก debug, pointer, tile และ mapper จากเกมง่ายๆเริ่ม NES/FC
อยากทำแพตช์ไทยที่จบได้เร็วที่สุดเลือกเกม SFC ที่มี text engine เข้าใจง่าย
อยากแปล RPG เนื้อเรื่องยาวเลือก SFC
เกม NES เดิมมี MMC3/CHR bank เหลือ และข้อความสั้นNES ยังน่าทำ
เกม NES เป็น NROM/Mapper 0 และ tile เต็มเลี่ยง หรือยอมทำเฉพาะ menu/partial translation
อยากได้ภาษาไทยที่วรรณยุกต์อ่านสวยและถูกต้องSFC
เป็นโปรเจกต์แรกและยังไม่รู้ assemblyNES เพื่อเรียนพื้นฐาน แล้วขยับ SFC

7. อย่าเลือกจาก "เครื่อง" อย่างเดียว — ให้เลือกจาก "รูปแบบฟอนต์ของเกม"

ปัญหาหลักของงานแปลไม่ใช่แค่ถอด .tbl หรือย้าย pointer ได้ แต่คือ เกมวาดฟอนต์อย่างไร และฟอนต์นั้นใช้ร่วมกับอะไรบ้าง ต่อให้เลือก SFC แล้ว ถ้าฟอนต์ในเกมนั้นจัดวางแบบซับซ้อน ก็ยังจบยากอยู่ดี

✓ เกมที่แปลจบง่าย ควรมีลักษณะนี้

  • กล่องบทสนทนาใช้ฟอนต์ชุดเดียวเป็นหลัก
  • ฟอนต์บทสนทนาอ่านไทยได้ เช่น logical cell 8×16 หรือ 16×16
  • ฟอนต์ไม่ได้ใช้ปนกับฉาก, sprite, ไอคอน, battle effect
  • เปลี่ยน tile ได้โดยไม่กระทบหลายหน้าจอ
  • ข้อความไม่ถูกบีบอัด หรืออย่างน้อยหา decoder ได้ง่าย
  • ข้อความยาวขึ้นแล้วมีวิธีขยาย/ย้าย script ได้
  • ไม่มี VWF หรือมีแต่เข้าใจง่าย

✕ เกมที่ควรเลี่ยงสำหรับโปรเจกต์แรก

  • dialogue ใช้ 8×8 แต่ menu ใช้ 8×16 หรือสลับไปมาบ่อย
  • ฟอนต์เดียวกันถูกใช้เป็นทั้งข้อความและ UI/icon
  • tile/font ถูกบีบอัด และโหลดใหม่แทบทุกฉาก
  • ใช้ font แบบ dynamic (โหลดเฉพาะตัวที่ต้องใช้เข้า VRAM)
  • มี VWF, ruby text, portrait/name window หลายระบบ
  • text เข้ารหัส/บีบอัด และ pointer กระจายหลาย bank พร้อมกัน
  • ใช้ชิปเสริม เช่น SA-1, Super FX ถ้ายังไม่คุ้น 65816

8. กรณีศึกษา: ฟอนต์ 8×8 ปนกับ 8×16 ในเกมเดียว

โปรเจกต์ GBA เกมหนึ่งแปลจบสมบูรณ์ทั้งเกม แต่ระหว่างทางพบว่าเกมใช้ฟอนต์ 8×8 และ 8×16 พร้อมกัน คนละจุดในเกมเดียว ทีมงานพยายามบังคับให้จุดที่เป็น 8×8 กลายเป็น 8×16 เพื่อให้ตัวไทยอ่านง่ายขึ้นสม่ำเสมอทั้งเกม — แต่ยิ่งแก้ยิ่งพัง สุดท้ายตัดสินใจ จบแพตช์ด้วยฟอนต์ 8×16 เฉพาะจุดที่รองรับได้จริง และปล่อยจุด 8×8 ไว้ตามเดิม

นี่เป็นการตัดสินใจที่ถูกต้อง เพราะถ้า engine เดิมกำหนดว่าตัวอักษรหนึ่งตัวกินพื้นที่ 8×8 แล้วพยายามบังคับให้เป็น 8×16 มักเกิดปัญหาต่อเนื่อง เช่น ตัวถัดไปถูกวาดทับครึ่งล่างของตัวก่อน, line spacing เดิมไม่พอ, cursor/ตำแหน่งขึ้นบรรทัดยังขยับทีละ 8 pixel, tilemap/tile index/stride ของ routine ถูกออกแบบสำหรับ 8×8 มาแต่แรก, เมนูหรือหน้าจออื่นที่แชร์ renderer เดียวกันพังตาม, และสระล่าง/วรรณยุกต์ไทยชนกัน

บน SFC ก็เจอแนวคิดคล้ายกัน: แม้ BG จะตั้งขนาด cell เป็น 8×8 หรือ 16×16 ได้ แต่ "16×16" โดยหลักคือการอ้างถึงกลุ่ม tile 8×8 แบบ 2×2 ไม่ใช่ฟอนต์ 16×16 อิสระหนึ่งก้อน (อ้างอิง: Super Famicom Wiki, NESdev Wiki)

ข้อสรุปสำหรับงานที่ต้องการจบเร็ว:

เลือกเกมที่ dialogue เป็น 8×16/16×16 อยู่แล้ว ดีกว่าเขียน engine เพื่อยกระดับ 8×8 เป็น 8×16 เอง · ถ้าเกมเป็น 8×8 จริง ให้ยอมออกแบบฟอนต์ไทย 8×8 สำหรับเกมนั้นไปเลย แต่อย่าตั้งเป็นเป้าหมายแรกสำหรับเกมเนื้อเรื่องยาว

9. วิธีคัดเกมก่อนเริ่มจริง: แบบทดสอบ Feasibility

10. ขั้นตอนทดสอบจริงแบบสั้นที่สุด

1) ทดสอบข้อความก่อน

ใช้เครื่องมือ .tbl ที่มี: หา dialogue สั้นๆ ที่เห็นชัด → เปลี่ยนเป็นข้อความอังกฤษอื่นที่ยาวเท่าเดิม → ทดสอบหลายจุด (บทสนทนา, เมนู, ไอเทม, ชื่อศัตรู, save screen) → จดว่าแต่ละส่วนใช้ table/font เดียวกันหรือไม่ หากแค่เปลี่ยนข้อความแล้วจบง่าย แปลว่า script layer ผ่านด่านแรก

2) หา "ฟอนต์บทสนทนา" ไม่ใช่แค่ฟอนต์ใน ROM

เปิดเกมด้วย Mesen-S แล้วดู VRAM/tilemap ขณะมีกล่องข้อความบนจอ ตอบ 4 คำถามนี้: ข้อความอยู่ BG layer ไหน? glyph จริงเป็น 8×8 หรือสูง 16 pixel? ฟอนต์ dialogue อยู่ร่วมกับ tile ฉากหรือ UI ไหม? เปิด dialogue คนละฉากแล้ว font tile เปลี่ยนหรือไม่?

จุดสำคัญไม่ใช่ "SFC ใส่ tile ได้มากกว่าไหม" อย่างเดียว แต่คือ VRAM ของเกมนั้นเหลือที่ให้ font ไทยหรือเปล่า

3) แก้ glyph ทดลองเพียง 1 ตัว

อย่าเพิ่งวาดฟอนต์ไทยครบชุด: เลือกตัวอังกฤษที่ใช้ไม่บ่อย เช่น Q, X, Z → เปลี่ยนเป็น glyph ไทยทดลอง เช่น ก, า, ่ → เข้าให้ครบทุกหน้าจอ → ตรวจว่ามี graphics อื่นพังไหม

4) ทดสอบไทยหนึ่งประโยค "ที่ยาก"

อย่าทดสอบแค่คำสั้นๆ ให้ใช้ประโยคที่มีสระและวรรณยุกต์ครบ เช่น "นี่คือข้อความภาษาไทย" ถ้าเกมรองรับเพียง 8×8 ให้ดูตั้งแต่ต้นว่ายอมรับรูปแบบนี้ได้หรือไม่: สระบนวางเป็น tile แถวบน, ตัวหลักอยู่แถวกลาง, สระล่างวางเป็น tile แถวล่าง, วรรณยุกต์ซ้อนกับสระบนหรือไม่ — ถ้าต้องแก้ renderer ตั้งแต่ประโยคแรก เกมนั้นไม่ใช่ตัวเลือก "จบเร็ว" เว้นแต่ตั้งใจทำ engine ไทยจริงจัง

12. ชุดเครื่องมือขั้นต่ำสำหรับ "คัดเกม"

ไม่ต้องตั้งเครื่องมือหนักตั้งแต่แรก ใช้เพียง:

  • Mesen-S: ดู VRAM, tilemap, palette, CPU debugger และตามว่าฟอนต์ถูกโหลดตอนไหน
  • โปรแกรมแก้ hex: ค้นหา/แก้ byte และเทียบ ROM
  • เครื่องมือ .tbl เดิม: dump/insert ข้อความ
  • YY-CHR หรือ Tile Molester: ดูและแก้ tile graphics ใน ROM
  • Floating IPS: สร้าง BPS patch เมื่อเริ่มปล่อยทดสอบ
  • Git: เก็บ .tbl, script แปล, บันทึก address และ patch source

รายชื่อเครื่องมือ SFC สำหรับ ROM hacking แบบละเอียดกว่านี้ดูได้ที่ SNESLab Wiki · สิ่งที่เห็นใน VRAM ผ่าน Mesen เป็นข้อมูลขณะรันเท่านั้น ไม่ได้แปลว่าแก้ตรงนั้นแล้วจะบันทึกกลับ ROM ได้เสมอไป ต้องตามกลับไปแก้ที่ต้นทาง (ROM/routine) เสมอ

13. สรุป

  • NES/FC: เข้าใจง่ายกว่า แต่เป็นเครื่องที่ "ต้องประหยัดทุกไบต์ ทุก tile ทุก cycle"
  • SNES/SFC: reverse engineering ซับซ้อนกว่าตอนเริ่ม แต่เหมาะกับการดัดแปลงภาษาไทยมากกว่าอย่างมีนัยสำคัญ
  • ถ้าเคยเจอปัญหา tile ไม่พอบน FC มาก่อน เปลี่ยนไปทำ SFC จะช่วยได้มาก แต่ยังควรวิเคราะห์ VRAM และ graphics layout ของเกมก่อนเริ่มแปลเสมอ
ถ้าจะเลือกเกม SFC สำหรับโปรเจกต์แรก ให้เลือกเกมที่มี กล่องข้อความแบบ fixed-width, ฟอนต์ 8×8/8×16, script ไม่บีบอัด และไม่มี VWF เพราะจะลดความยากลงมากที่สุด

ตั้งกฎเลือกเกมของตัวเองไว้ล่วงหน้า เช่น:

"จะรับเฉพาะเกมที่ dialogue หลักใช้ฟอนต์ logical height 16 pixel, มี font bank เดียวหรือแยก dialogue ชัดเจน, และเปลี่ยนตัวทดลอง 3 ตัวแล้วไม่มีหน้าจอหลักพัง" — ถ้าเกมไม่ผ่านกฎนี้ ให้คัดออกทันที แม้จะเป็นเกมที่ชอบมาก เพราะงานแปลที่ "จบ" สำคัญกว่างานที่เริ่มง่ายแต่ติด engine กลางทาง

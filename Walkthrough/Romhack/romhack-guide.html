1. ROM Hack คืออะไร

การแปลเกมเก่า (NES/Famicom, SNES/SFC) เป็นภาษาไทย ไม่ใช่แค่ "เปลี่ยนตัวหนังสือ" แต่คือการ วิศวกรรมย้อนกลับ (Reverse Engineering) เข้าไปในตัวเกม แล้วดัดแปลงระบบทั้งข้อมูล ฟอนต์ และโค้ดที่วาดข้อความ ให้รองรับภาษาไทยได้จริงบนฮาร์ดแวร์ที่ไม่เคยถูกออกแบบมาให้รองรับภาษาไทยเลย

บทความนี้สรุปเป็น "แผนงาน" (Pipeline) ที่ใช้ได้จริงกับงานแปลเกมคอนโซลย้อนยุค เรียงจากขั้นสำรวจไปจนถึงขั้นแก้ปัญหากราฟิกระดับ Scanline เขียนให้เข้าใจง่ายด้วยการเทียบกับ "การรีโนเวทบ้านเก่า" — เห็นภาพรวมก่อน แล้วค่อยลงรายละเอียดทีละจุด

หน้านี้จะทยอยอัปเดตเพิ่มเติมตามที่ลงมือทำจริง — เก็บไว้เป็นบันทึกอ้างอิงระยะยาว

บทความนี้แยกเป็น 4 หน้า กดแท็บด้านบนเพื่อสลับไปอ่านหน้าอื่นได้ทุกเมื่อ:
  1. บทนำ (หน้านี้) — ภาพรวม 6 ขั้นตอน + กฎที่ต้องรู้ก่อนเริ่ม
  2. กรรมวิธี SFC เต็มรูปแบบ — ขั้นตอนละเอียดแบบเป็นเฟส, โครงสร้างโปรเจกต์, Milestone
  3. ปัญหา Tile บน NES/FC — ทำไม "ขยาย ROM + แก้ Pointer" อย่างเดียวไม่พอ และทางแก้ 5 แบบ
  4. เลือกเครื่อง/เลือกเกม — เทียบ NES กับ SNES + แบบทดสอบให้คะแนนก่อนเริ่มโปรเจกต์จริง

│
├── 1. ขั้นสำรวจและจำลองสภาพแวดล้อม (Exploration & Baseline)
│   ├── วิเคราะห์ ROM: Mapper, Header, PRG/CHR Bank, ชิปพิเศษ
│   ├── Version Control: Git Repo, Hash/Checksum, BPS/IPS Patch
│   └── วิเคราะห์ระบบเดิม: Trace การอ่านข้อความ, Pointer Table
│
├── 2. ชั้นข้อมูลและข้อความ (Script & Text Layer)
│   ├── ถอดรหัส: ไฟล์ตาราง (.tbl), Encoding, Control Codes
│   ├── จัดการพื้นที่: Expand ROM, หา Freespace, ย้าย Pointer
│   └── ความปลอดภัย: ตรวจ Terminator + Logic ตัดบรรทัด (Word Wrap)
│
├── 3. ชั้นการวาดและการแสดงผล (Rendering & Font Layer)
│   ├── จัดการ Tile (PPU/VRAM): ขนาดฟอนต์ 8x8/8x16/16x16,
│   │   CHR Bank Switching, VRAM Management ช่วง VBlank
│   └── ออกแบบฟอนต์ไทย: Prototype (glyph สำเร็จรูป ก่ ก้ กิ)
│       → Engine (วางสระ/วรรณยุกต์ประกอบ + กำหนด Offset)
│
└── 4. ชั้นการแก้ไขระบบ (Engine Hooking & Patching)
    ├── เขียน Patch: 65C816/6502 Assembly, Hook, Trampoline
    ├── IRQ/Scanline: Trace ด้วย Lua, เพิ่ม Entry ในตาราง IRQ เดิม,
    │   Exit Hook รีเซ็ต IRQ State กัน State Leak
    └── ทดสอบ: Regression Test ทุกหน้าจอ + Build Script อัตโนมัติ

3. รายละเอียดแต่ละขั้นตอน

ขั้น 1 — สำรวจโครงสร้าง (ดูพิมพ์เขียว)

ทำอะไร: เปิดดูข้อมูลในตัวเกมว่าใช้ "กฎ" แบบไหน — ใช้ Mapper อะไร มีชิปพิเศษไหม พื้นที่ตรงไหนว่าง

คิดง่ายๆ: เหมือนไปดูบ้านเก่าก่อนรีโนเวท ว่าเสาต้นไหนย้ายได้ ผนังไหนห้ามทุบ

เครื่องมือ: Mesen-S (emulator ที่มี debugger ในตัว ใช้ส่องว่าเกมทำงานอย่างไรตอนรันจริง)

ขั้น 2 — ขยายพื้นที่ (ต่อเติมห้องเก็บของ)

ทำอะไร: พื้นที่เดิมในตัวเกมมักเต็มอยู่แล้ว ต้อง "ขยาย ROM" (Expand ROM) เพื่อเปิดพื้นที่ว่างใหม่ไว้ใส่ข้อความ/ฟอนต์ไทย

คิดง่ายๆ: เหมือนต่อเติมหลังบ้านเพื่อเก็บเฟอร์นิเจอร์ใหม่ (ตัวอักษรไทยของเรา)

เครื่องมือ: HxD หรือ ImHex (hex editor ใช้ดู/แก้ไบต์ดิบของไฟล์ ROM)

⚠️ บน NES/FC ขั้นตอนนี้ซับซ้อนกว่าที่คิด เพราะ "พื้นที่เก็บข้อความ" (PRG-ROM) กับ "พื้นที่เก็บรูปตัวอักษรที่จอมองเห็นพร้อมกัน" (CHR/VRAM) เป็นคนละเรื่องกัน ขยาย ROM แล้วแก้ Pointer อย่างเดียวไม่พอเสมอไป — อ่านรายละเอียดที่ หน้าปัญหา Tile บน NES/FC

ขั้น 3 — จัดระบบภาษา (ทำตารางถอดรหัส)

ทำอะไร: เกมเดิมรู้จักแค่ A-Z เราต้องสอนให้มันรู้จัก ก-ฮ โดยทำ "สมุดจด" (Table file / .tbl) บอกว่ารหัสไบต์ไหน = ตัวอักษรอะไร

คิดง่ายๆ: เหมือนทำสมุดล่าม แปลจาก "ภาษาเกม" (ตัวเลข) ให้เป็น "ภาษาเรา" (ตัวอักษรไทย)

เครื่องมือ: โปรแกรมจดบันทึกทั่วไป + เครื่องมือทำ Table ของสายนักแปลรอมแฮก

ขั้น 4 — แก้ระบบวาด (สร้างฟอนต์ไทย)

ทำอะไร: วาดรูปตัวอักษรไทยลงไปแทนที่ตัวอักษรอังกฤษที่ไม่ได้ใช้ในเกม (หรือพื้นที่กราฟิกที่ขยายเพิ่ม)

คิดง่ายๆ: เหมือนทาสีใหม่ เปลี่ยนป้ายหน้าห้องจากภาษาอังกฤษเป็นภาษาไทย

เครื่องมือ: YY-CHR (โปรแกรมวาดพิกเซลฟอนต์/กราฟิกของเกม NES/SNES โดยเฉพาะ)

ขั้น 5 — เชื่อมต่อระบบ (สร้างสะพานเชื่อม)

ทำอะไร: ภาษาไทยมักยาวกว่าอังกฤษ และมีสระบน/ล่างที่ต้องวางซ้อนตัวพยัญชนะ ต้องเขียน "คำสั่งใหม่" (ASM) บอกเกมว่า "เจอ ก ให้วาดแบบนี้ เจอสระอิ ให้วางซ้อนด้านบน"

คิดง่ายๆ: เหมือนเดินสายไฟ/ประปาใหม่ ให้บ้านใช้งานได้จริงตามที่ต้องการ ไม่ใช่แค่มีห้องเฉยๆ

เครื่องมือ: Asar (ตัวประกอบโค้ด 65816/6502 assembly ยิงแพตช์เข้าไปในเกม)

ขั้น 6 — ตรวจสอบ (ทดสอบใช้งานจริง)

ทำอะไร: เล่นไล่ทุกหน้าจอ ดูว่ามีจุดไหนภาพพัง ข้อความล้นกล่อง หรือกราฟิกทับกันไหม

คิดง่ายๆ: เหมือนตรวจรับบ้านก่อนย้ายเข้าอยู่จริง — เจอจุดพังตอนนี้ถูกกว่าเจอตอนแจกแพตช์ไปแล้ว

4. ข้อจำกัดของฮาร์ดแวร์

  • Mapper Constraints: ต้องเข้าใจ Mapper ของเกมก่อน (เช่น MMC3, Bandai FCG / Mapper 159) เพื่อดึงศักยภาพการสลับ CHR Bank มาเพิ่มพื้นที่เก็บฟอนต์ไทย
  • VRAM Ownership: ต้นตอของปัญหา "กราฟิกขยะ" ส่วนใหญ่คือการแย่งชิงพื้นที่ใน VRAM ระหว่าง UI/ฉากเดิมของเกม กับฟอนต์ไทยที่เราเพิ่มเข้าไป
  • Rendering Logic (SFC): ถ้าเกมรองรับคันจิอยู่แล้ว ให้ใช้ประโยชน์จากพื้นที่ตัวอักษรขนาด 16x16 พิกเซล จะลดความซับซ้อนตอนประกอบสระ/วรรณยุกต์ไทยได้มาก

5. จุดยากที่สุด: กลยุทธ์แก้ IRQ/Scanline

นี่คือจุดที่งานแปลเกมมักไปสะดุด เพราะเป็นปัญหาระดับจังหวะเวลาการวาดภาพของฮาร์ดแวร์จริง ไม่ใช่แค่เรื่องข้อมูล

Relative Timing: การทำ IRQ ต้องคำนึงถึงค่า Scroll (เช่น $33) ของเกมด้วย เพราะตำแหน่งกล่องข้อความบนจอไม่ได้อยู่นิ่งตลอดเวลา
Race Condition: อย่าเขียน IRQ Handler แยกต่างหากจากระบบเกม — ควร Hook เข้าตาราง IRQ เดิม ที่มีอยู่แล้ว (เช่น $D2CA) เพื่อความปลอดภัยและลดโอกาสชนกับของเดิม
State Cleanup: ทุกครั้งที่ปิดหน้าต่างข้อความ ต้องคืนค่า Registers (A, X, Y) และรีเซ็ต IRQ Index (เช่น $6D) อย่างเด็ดขาด ไม่งั้นสถานะที่ค้างอยู่จะ "รั่ว" ไปทำให้หน้าจอถัดไปพังโดยไม่รู้สาเหตุ

วิธีวิเคราะห์: ใช้ Lua script trace ดูว่า Scanline ไหนถูกวาดซ้อนทับกัน (Scanline Overlap) ก่อนตัดสินใจแก้โค้ด

6. กฎเหล็กของนักแปลเกม (The Hacking Discipline)

  1. Don't Re-invent the Wheel: ถ้าเกมมีระบบคันจิหรือระบบสลับ Bank ของตัวเองอยู่แล้ว ให้พยายาม Hook เข้าระบบเดิม แทนการเขียน Renderer ใหม่ทั้งหมด
  2. Incremental Build: ใช้สคริปต์ (Python/Asar) สร้าง Patch เสมอ เพื่อให้แก้ไขซ้ำได้ (Reproducible) และย้อนกลับได้ (Rollback) ทุกครั้งที่พลาด
  3. Feasibility First: อย่าเพิ่งลงมือแปลทั้งเกม — ทำ Feasibility Test ให้ผ่านครบกระบวนการในหน้าจอเดียวก่อน ค่อยขยายเป็นแพตช์ขนาดใหญ่ (มีแบบทดสอบให้คะแนนพร้อมใช้ที่ หน้าเลือกเครื่อง/เลือกเกม)

7. กฎทอง ไม่ให้ "เสียของ"

  1. อย่าแปลทั้งเกมตั้งแต่วันแรก: ลองแปลแค่ "1 ประโยค" ให้จบกระบวนการก่อน ถ้าทำสำเร็จ จะรู้ทันทีว่าต้องแก้ตรงไหนบ้าง ดีกว่าแปลเป็นหมื่นคำแล้วมาพบว่าทำไม่ได้ทีหลัง
  2. เครื่องเกมมีข้อจำกัดเรื่อง "ที่วางภาพ": ต่อให้เพิ่มพื้นที่เก็บข้อความได้เยอะแค่ไหน แต่ VRAM (ที่วางตัวอักษรจริง) มีจำกัดเสมอ เหมือนโต๊ะทำงานที่วางของได้จำกัด — เอาของใหม่มาวางโดยไม่ขยับของเก่า ภาพจะทับกันหรือกลายเป็นขยะ
  3. อย่าแก้ไฟล์ต้นฉบับโดยตรง: เก็บ ROM ตัวจริงไว้ที่ปลอดภัย แล้วทำงานกับ "ไฟล์สำเนา" เสมอ พลาดแล้วเกมพัง ยังย้อนกลับมาเริ่มใหม่ได้
  4. ใช้เครื่องมือสร้าง Patch เสมอ: แทนที่จะแจก ROM เต็มไฟล์ ให้สร้าง Patch (เหมือนไฟล์อัปเดตเล็กๆ ที่แปะทับ ROM ต้นฉบับ) ปลอดภัยกว่าและถูกกฎมากกว่า

9. สรุปส่งท้าย

มองว่านี่คือการ "ดัดแปลงระบบ" ไม่ใช่แค่การแปลภาษา — ถ้าควบคุมการวาดภาพและการแสดงผลของเกมได้ ภาษาอะไรก็แปลได้

อ่านต่อได้ที่ 3 หน้านี้ ตามสิ่งที่กำลังติดปัญหาอยู่:

  • กรรมวิธี SFC เต็มรูปแบบ — ถ้าพร้อมลงมือทำจริงแล้วอยากได้แผนงานละเอียดทีละเฟส
  • ปัญหา Tile บน NES/FC — ถ้าทำ NES/FC แล้วเจอปัญหา "tile ไม่พอ" หรือฟอนต์ขึ้นผิด
  • เลือกเครื่อง/เลือกเกม — ถ้ายังไม่ได้เลือกเกม อยากรู้ว่าเกมไหนมีโอกาสแปล "จบ" มากกว่า

หัวข้อที่ยังไม่ลงรายละเอียด (รอเพิ่มทีหลัง): ตัวอย่าง Lua script สำหรับ trace แบบเต็ม, โครง Build Script อัตโนมัติ, ตัวอย่างจริงของการต่อ Combining Marks ภาษาไทย
